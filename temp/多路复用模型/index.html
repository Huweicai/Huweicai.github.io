输入输出

输入输出是冯·诺依曼结构型计算机中一个非常重要的组成部分，一台计算机中除了计算单元和内存其他的组成设备都可以抽象成I/O设备，比如：网卡、磁盘、键盘鼠标、耳机音响显示器。

文件

Unix 类系统把所有的 I/O 设备都抽象成了一个文件，文件具有 read 和 write 两种方法。在 Linux 中，文件以文件描述符（FileDescriptor：FD）的方式表示，FD 在 Linux 的 API 中是一个非负的 int 数字，而在 64位机器上，int 是一个 64位的数字，所以理论上最大打开文件的数量是：2^63-1 = 9223372036854775807，但是这个通常受内存等很多因素的限制，最直接的内核会限制打开文件的最大数量，可以通过修改和查看文件 /proc/sys/fs/file-max 来设置：

$ cat /proc/sys/fs/file-max
输出：98304

Linux 下可以通过命令 lsof ( LiSt Open Files) 来查看打开的文件，这给了我们一个粗略查看当前系统打开文件数量的方式：

$ lsof | wc -l
输出：22722

但是 lsof 会重复计算被进程共享的 FD，直接获取内核的信息会更加精确：

$ cat /proc/sys/fs/file-nr
输出：4320	0	98304
# 打开了 4320 个文件

所有打开的文件由三个相关的数据结构表示：

进程文件描述符表

这是一个每个进程私有的数据结构，存储了当前进程打开的所有文件。Linux 源码中的进程实体是一个位于 /include/linux/sched.h 头文件下的 task_struct结构体，这个结构体中会有一个files_struct结构体在注释中赫然写着：/* Open file information: */，存放了所有打开文件的信息。files_struct 中有一个 fdtable 构体，这就是进程文件描述附表的源码实现，定义于：/include/linux/fdtable.h文件中：

struct fdtable {
	unsigned int max_fds;	 // 当前进程的最大打开文件数量
	struct file __rcu **fd; // fd 数组
	unsigned long *close_on_exec;
	unsigned long *open_fds;	
	unsigned long *full_fds_bits;
	struct rcu_head rcu;
};

而我们打开一个文件获得的 FD 本质上就是这个 fdtable 结构体的 fd 字段对应数组的索引。

这个数组的前三个元素永远是内核的默认 FD：

  • 0: 标准输入
  • 1: 标准输出
  • 2: 标准错误输出

所以用户打开的文件描述符都是从 3 开始的。

系统打开文件表

我们刚刚说到 FD 其实是进程文件描述符表的索引，而这个索引对应的值则是一个 file 对象，定义于：include/linusx/fs.h文件中，主要包括文件路径、打开模式、当前位置等信息：

struct file {
    struct list_head f_list; // 所有打开的文件形成一个双向链表
    struct dentry *f_dentry; // 指向相关目录项的指针
    struct vfsmount *f_vfsmnt; // 指向 VFS 安装点的指针
    struct file_operations *f_op; // 指向文件操作表的指针
    mode_t f_mode; // 文件的打开模式：只读、追加等
    loff_t f_pos; // 文件的当前位置，打开时默认为0，可以通过 seek 修改
    unsigned short f_flags; // 打开文件时所指定的标志
    unsigned short f_count; // 进程计数，到 0 后就可以释放
    unsigned long f_reada, f_ramax, f_raend, f_ralen, f_rawin;
    // 预读标志、要预读的最多页面数、上次预读后的文件指针、预读的字节数以及 
    预读的页面数
    int f_owner; // 过信号进行异步 I/O 数据的传送
    unsigned int f_uid, f_gid; /*用户的 UID 和 GID*/
    int f_error; // 网络写操作的错误码
    unsigned long f_version; // 版本号
    void *private_data; // 供 tty 驱动程序使用
};

系统打开文件表，则是一个由 file 对象串联而成的双向链表，之所以设计成独立于进程之外的结构主要是考虑到多个进程间共享文件的场景，如：fork出来的父子进程之间。

每次打开文件都会创建一个新的 file 对象以及得到一个新的 fd，比如你可能会需要读这个文件的不同位置，但是它们底层指向的是同一个 inode 指针。

I-node表

上面我们提到了 inode 这种数据结构，inode 代表了一个文件，并不关心文件名和路径，因为不同路径名称的两个文件可能还是最终链接到了同一个底层文件。

    kdev_t i_rdev; /*实际设备标识号*/
