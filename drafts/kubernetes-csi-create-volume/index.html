容器附加存储

通常在容器化的系统架构中，我们通常会将服务设计成无状态的，便于更好的动态扩缩容及升级服务。但走整个软件系统中，这个 状态并不会凭空消失，只是继续转移到了下层，通常来说这个下层会是一层持久化的分布式存储，这个存储可能是结构化的，如: MySQL、Redis、ETCD这种数据库，也有可能是原始的文件系统和块，本文我们主要关注后者，即容器附加存储（Container Attached Storage）。

以容器架构平台的代表者 Kubernetes 为例，为了帮助用户更好的使用分布式存储，引入了卷的概念，这样我们就可以直接通过与 Kubernetes 的 API 交互即可轻松完成分布式存储的申请、挂载卸载和删除，而不至于让我们每次在容器起来的时候手动下载文件系统客户端，然后运行各种命令连接上文件存储后端再挂载才能实现访问。

CSI

基本概念

Container Storage Interface (CSI)是一组容器存储接口，分布式存储提供者只需要实现这个这个接口，既可以同时为 Mesos、Kubernetes等容器平台提供存储服务。

CSI 要求能力提供者实现两个插件，提供 GRPC 服务：

  • 节点插件：每台节点上运行一个，用于实际在机器上挂载卷
  • 控制插件：运行一个实例即可，用于管理卷的生命周期

其次 CSI 申明了三组 GRPC 接口需要在这两个插件上实现：

  1. 身份接口：调度和控制插件都需要实现，和返回一些基本元信息

    GetPluginInfo()  //返回driver的信息，比如名字，版本
GetPluginCapabilities()   //返回driver提供的能力，比如是否提供Controller Service,volume 访问能能力
Probe()   //探针

  2. 控制接口：控制插件实现，提供卷的增删改查等生命周期管理

    CreateVolume() //创建卷
DeleteVolume() //删除卷
ControllerPublishVolume() //attach 卷
ControllerUnpublishVolume() //unattach卷
ValidateVolumeCapabilities() //返回存储卷的功能点，如是否支持挂载到多个节点上，是否支持多个节点同时读写
ListVolumes() //列出所有卷
GetCapacity() //返回存储资源池的可用空间大小
ControllerGetCapabilities() //返回controller插件的功能点，如是否支持GetCapacity接口，是否支持snapshot功能等
CreateSnapshot() //创建快照
DeleteSnapshot() //删除快照
ListSnapshots() //列出快照
ControllerExpandVolume() //扩容
ControllerGetVolume() //获得卷

  3. 节点接口：节点实际在机器上操作卷相关操作

    NodeStageVolume() //将存储卷格式化并挂载至临时 globalmount 目录
NodeUnstageVolume() //NodeStageVolume的逆操作，将一个存储卷从临时目录卸载
NodePublishVolume() //将存储卷从临时目录mount到目标目录（pod目录）
NodeUnpublishVolume() //将存储卷从pod目录umount掉
NodeGetVolumeStats() //返回可用于该卷的卷容量统计信息。
NodeExpandVolume() //noe上执行卷扩容()
NodeGetCapabilities() //返回Node插件的功能点，如是否支持stage/unstage功能
NodeGetInfo() //返回节点信息

kubernetes、mesos 等容器平台等相关的组件在用户需要对应的存储能力时，则会去调用这两个插件提供的服务上对应的接口，插件的提供者则不用再关心具体的流程了，而容器平台也无需关注存储底层是如何实现和组织的。

CSI In Kubernetes

CSI 在 k8sv1.9  版本引入，并在v1.13发布为正式版本。在 CSI 引入之前，k8s也是支持 pv、pvc 的，不过是 in-tree代码块的方式来实现的，即卷的客户端实现是直接被嵌在 kubelet 组件中的，这样维护起来很不方便，也不利于扩展，任何这一块儿的改动都得等k8s发版然后再上线，并且负责 k8s 代码仓库维护的同学对存储这一块儿也不一定很熟悉，代码的测试和迭代也相对困难。

有了 CSI 之后，开发者就可以通过插件的方式来灵活的提供持久化存储的能力。

目前仍有gce 、aws 、azure 、ceph等持久卷实现仍是in-tree模式实现的，正在逐步迁移中，未来 k8s 社区计划将所有in-tree的持久卷实现都迁移到 CSI 模式来实现，仅保留 hostPath、 emptyDir等本地卷实现即可。

相关K8S对象

卷相关对象

PersistVolume

PV，持久卷，整个k8s存储体系的核心，一个 PV 对象代表了一块对应的分布式存储卷。

apiVersion: v1
kind: PersistentVolume
metadata: 
  name: "test-pv"
spec:
  capacity: # PV的容量
    storage: 10Gi
  csi:
    driver: com.tencent.cloud.csi.cosfs # CSI驱动
    readOnly: false
    fsType: ext4 # 要挂载的文件系统，需要host支持
    volumeAttributes: # map[string]string 自定义属性
    nodePublishSecretRef: # 指定相关的 secret
      name: test-secret
  accessModes: # 支持的读写模式
    - ReadWriteOnce # 单机读写
    - ReadOnlyMany # 多机只读
    - ReadWriteMany # 多机读写
  claimRef: # 指向对应的PVC
    apiVersion: v1
    kind: PersistentVolumeClaim
    name: huweicai-test-vpc
    namespace: test 
  persistentVolumeReclaimPolicy: Delete / Retain # 解除绑定的回收策略，自动创建的默认删除，手动的默认保留
  storageClassName: "" # 制作该PV的StorageClass
  mountOptions: # 挂载选项
  volumeMode: Filesystem # 卷模式，块设备 or 文件系统(D)
  nodeAffinity: # 通过节点选择器指定亲和性

PersistentVolumeClaims

PVC，顾名思义 PV 的请求，代表了用户对于PV的请求，同时携带了详细的关于具体PV需求的信息。

当集群中有配置动态提供卷的策略（StorageClass）时，CSI provisioner 会回应用户的 PVC 提供存储卷并创建对应的 PV 对象。

apiVersion: v1
kind: PersistentVolumeClaim
spec:
  accessModes: # 访问模式
    - ReadOnlyMany  # 多机只读
    - ReadWriteMany # 多机读写
    - ReadWriteOnce # 单机读写
  selector: # PV选择器
  resources: # 需要的容量
    requests:
      storage: 5Gi
  storageClassName: "指定使用哪个StorageClass，否则使用默认的"
  volumeMode: # Block | Filesystem 两种挂载模式

StorageClass

StorageClass 对象用于在集群中动态提供持久卷，不然管理员就只能先跟用户沟通确定好需求然后手动创建 PV 让用户去绑定了。

apiVersion: storage.k8s.io/v1
kind: StorageClass
provisioner: "rook-ceph.rbd.csi.ceph.com" # 底层CSI名
parameters: # 透传给 CSI 的参数
reclaimPolicy:  Recycle/Retain/Delete # PVC释放时处理PV的策略：回收、保留、删除
mountOptions:
  - dir_mode=0777
  - file_mode=0777
allowVolumeExpansion: true # 是否允许卷扩容
volumeBindingMode: Immediate/WaitForFirstConsumer # PV创建策略，立即创建or按需延迟创建

VolumeAttachment

VolumeAttachment对象主要用于调度组件向插件组件传递调度的结果，保存了卷到节点的绑定关系：

apiVersion: storage.k8s.io/v1
kind: VolumeAttachment
metadata:
  creationTimestamp: "2021-07-02T02:45:50Z"
  name: csi-1e7260d50191c3cb3f81c3a4df2d65aa75c2bda5727604ec8d476d471684255e
spec:
  attacher: "对应CSI名称，由哪一个CSI组件来执行"
  nodeName: "对应的节点名称"
  source:
    persistentVolumeName: "持久卷名称"
status:
  attached: true # 状态

插件相关对象

CSIDriver

CSIDriver 对象代表了k8s集群中的一种 CSI 插件，持有一些插件的元信息供集群使用，由 cluster-driver-registrarsidecar 容器创建，但是其实目前来说这种对象作用不是那么的大，暂时只有

  1. 是否需要 Attach 流程
  2. 挂载时是否需要传递 POD 信息
  3. 是否支持 Ephemeral 卷

这三个功能。

apiVersion: storage.k8s.io/v1
kind: CSIDriver
metadata:
  name: rook-ceph.cephfs.csi.ceph.com
spec:
  attachRequired: true
  podInfoOnMount: false
  volumeLifecycleModes:
  - Persistent

CSINode

CSINode 代表了一个上面有 CSI插件 的 Node，和对应的 Node 同名，持有了相关的 CSI 插件信息，registrar向 kubelet注册插件信息时，kuelet 就会同时维护这个 CSINode对象。

apiVersion: storage.k8s.io/v1beta1
kind: CSINode
metadata:
  creationTimestamp: "2021-01-10T04:36:22Z"
  name: 10.1.1.10
  ownerReferences:
  - apiVersion: v1
    kind: Node
    name: 10.1.1.10
spec:
  drivers:
  - name: com.example.cloud.csi.cosfs
    nodeID: 10.1.1.10
    topologyKeys: null
  - name: com.example.cloud.csi.cfs
    nodeID: 10.1.1.10
  - name: csi.chubaofs.com
    nodeID: 10.1.1.10

插件组件

Aattacher

源码地址：https://github.com/kubernetes-csi/external-attacher

Attacher 主要用于 watch VolumeAttachment 对象，然后通过 unix socket 调用 csi grpc 服务对应的 ControllerPublishVolume 和 ControllerUnpublishVolume。

Provisioner

源码地址：https://github.com/kubernetes-csi/external-provisioner Provisioner，提供动态制卷能力，当监听到有新的 PVC 对象创建时，Provisioner 会调用 csi 服务对应的 CreateVolume来在远端存储上创建一块对应的卷，然后在k8s集群中创建一个 PV对象代表刚刚创建的这块远端卷。

当监听到PVC删除时也是一样的，释放PV并根据 StorageCalss设置的回收策略判断是否需要调用 DeleteVolume接口来真正删除远端存储卷。

Resizer

源码地址：https://github.com/kubernetes-csi/external-resizer

跟 Provisioner 一样 Resizer 也会监听 PVC 对象，不过 Provisioner 关注的是创建和删除这两个动作，而 Resizer 关注的则是扩容，当 PVC 里申明的容量发生变更后，Resizer 会调用 csi 服务的 ControllerExpandVolume来进行扩容。

Registrar

源码地址：https://github.com/kubernetes-csi/node-driver-registrar

Registrar 会调用csi 服务的NodeGetInfo并根据返回的信息通过调用kubelet的接口来将插件注册到 kubelet 上。
