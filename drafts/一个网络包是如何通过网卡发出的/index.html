一个网络包是如何通过网卡发出的
  • 2026-05-21
  • 5 minutes read
  • 2113 words

我们今天来探讨一下：一个网络包是怎么从网卡出去的？它完整的路径是什么？

回想一下，不管经典的 curl http://example.com 还是 ping example.com，这两种行为都发生在网络协议的上层，都会被一层一层地封装上传输层、网络层、数据链路层的头部，然后网络包封装完成了。

但是，接下来会发生什么呢？这个网络包又是怎么出去的呢？对端服务器的网络包又是怎么回来的呢？直觉上我们会知道这是网卡的功劳，印象中肯定也听过 DMA，ring buffer 这些词，但是具体呢？完整的链路呢？让我们来过一遍。

起点

不管是 ping 是 curl 是 dig，亦或是 C、Go、Java 等每种编程语言都会有各自的用户态 API，都些都是网络能力的入口。

具体的 API 可能长这样：

### C
#include <sys/socket.h>
#include <string.h>

// UDP
sendto(fd, "hello", 5, 0, (struct sockaddr *)&dst, sizeof(dst));

// TCP
connect(fd, (struct sockaddr *)&dst, sizeof(dst));   // 三次握手
send(fd, "hello", 5, 0);  // 发包

### Golang
conn, _ := net.Dial("udp", "127.0.0.1:9999")
conn.Write([]byte("hello"))

这些 API 对于网络的使用还是要通过操作系统 API 委托给内核执行的。

这里我们以 UDP 为例，协议更为简单，对应的系统调用是 sys_sendto。

内核协议栈

内核协议栈会是一个非常复杂且漫长的旅程，所以目前但凡是高性能网络方案要做的第一件事情就是 bypass 内核协议栈。

  sendto
  └ __sys_sendto → sock_sendmsg → inet_sendmsg
    └ udp_sendmsg                              [UDP]
       ├ ip_route_output_flow   (查路由 dst)
       ├ ip_make_skb            (__ip_append_data 拷数据 + __ip_make_skb 封 IP 头)
       ├ udp_send_skb           (UDP 头 + 校验和)
       └ ip_send_skb
          └ ip_local_out → __ip_local_out      [IP] (NF_LOCAL_OUT)
             └ dst_output → ip_output           (NF_POST_ROUTING)
                └ ip_finish_output → __ip_finish_output → ip_finish_output2  (查 ARP)
                   └ neigh_output → neigh_hh_output   [L2] (memcpy 二层头)
                      └ dev_queue_xmit → __dev_queue_xmit            [dev/qdisc]
                         └ __dev_xmit_skb → __qdisc_run → qdisc_restart → sch_direct_xmit
                            └ (validate_xmit_skb) → dev_hard_start_xmit
                               └ xmit_one → netdev_start_xmit → __netdev_start_xmit
                                  └ ndo_start_xmit                    [driver]
                                     └ ixgbe_xmit_frame → ixgbe_tx_map → writel(tail) 敲门铃
                                        └ NIC DMA 读描述符 → 上线

  1. sys_sendto 这是入口

  2. 会通过各种指针跳转到 udp_sendmsg 主要的逻辑都发生这个函数中

  3. udp_sendmsg首先会进行一系列的参数合法性检查

    1. 然后会有一个 eBPF 的 cgroup/sendmsg4 hook 点可以注入一些操作
    2. 通过 dst_rtable查当前连接的路由缓存，当然第一次请求大概率查不到
    3. 会通过 ip_route_output_flow查内核的 FIB 路由表，判断下一跳地址；通常是对应网卡的默认网关，当然有时候也会是同子网直连地址
    4. 同时这个函数内部，有大量的代码在处理 cork这个特性（小包合并成一次调用），花了很多代码去处理但是基本没啥人用的 feature，我们就不管了
    5. 继续调用ip_make_skb申请 skbuffer 配合查询出来的路由信息填充 IP 层的基础 header 字段，因为还有一部分字段需要等 UDP header 填完后才能确定；同时这个函数内会将用户的要发送的实际 payload 内容复制到 skbuffer 中，就是我们通常说的，用户态到内核态的数据复制

  4. 然后udp_sendmsg内部会调用 udp_send_skb ，填充 UDP Header，校验和，完成网络层的头部拼装；调用 ip_send_skb 发送

  5. ip_send_skb简单封装了ip_local_out对其返回值进行了打点统计

  6. ip_local_out 会完整整个三层头部生剩余字段的封口；函数末尾有一个 netfilter 的 hook LOCAL_OUT，很多防火墙的出方向包拦截规则就是在这个位置生效的

  7. dst_output -> ip_output ->ip_finish_output 这三个函数都没什么逻辑，又插了一个 eBPF 和 netfilter 的 hook

  8. 接下来到 __ip_finish_output ，这个函数会判断 MTU （当今互联网 99.9% 的情况下是 1500 字节），超过这个大小会将包进行 IP 分片；但是 99.9% 的情况下其实也不会分片，上层都自己处理了

  9. ip_finish_output2 内部会调用 ip_neigh_for_gw 查询邻居表（ARP 解析缓存）里面查出来的下一跳地址的 MAC 地址，然后调用neigh_output

  10. 如果命中了 MAC 缓存，则会直接调用 neigh_hh_output 拼装以太网协议头部；如果没有命中，则会走neigh_resolve_output对下一跳 IP 地址发起 ARP 解析，拿到地址后再拼装

  11. 到这里协议栈封装全部完成。但在交给网卡前还有一道排队机制 qdisc(Queueing Discipline):dev_queue_xmit 会先按流哈希(skb->hash)给包选定一个 TX 队列,每个 TX 队列各挂一棵自己的 qdisc 树,多队列之间并行出队、互不阻塞。同一条流恒定哈希到同一队列、保序;乱序只可能发生在不同流之间。

  12. qdisc 提供了干预包优先级与速率的抓手——大量进程同时提交包时,它决定谁先出队；tc(Traffic Control)就是基于 qdisc 实现的,常用于带宽不足时做 QoS,让重要的包先走；出队列之后网络包就会送入网卡驱动，这一块儿就不属于内核协议栈的地盘了

简单总结一下，其实这么庞大的一坨代码干的事情非常简单：

就是为了拼出来完整的网络包协议头，连带着中间插了很多钩子。

驱动

我们总说操作系统是对硬件的抽象，可抽象是有代价的，上层接口和协议栈设计得再优雅，last mile 上各个厂商设计的五花八门的不一样的、具体的网卡，总需要有人去面对 —— 干这个 dirty work 的，就是驱动。

具体到 code 层面来说，要实现一个网卡驱动，只需要实现 net_device_ops 这个接口即可，接口里面的函数很多，不过真正重要的其实就这几个：

  1. ndo_open / ndo_stop 网卡 up/down 时调用，负责相关资源初始化、申请与回收
  2. ndo_start_xmit 发包
  3. ndo_select_queue 队列选择负载均衡
  4. ndo_get_stats64 返回网卡内部数据统计

但是虽然说 Intel、Marvell、Realtek 等各种网卡方案，实现上各不相同，但是大体流程上仍然是殊途同归的，这是被接口约束以及市场和社区多年演进收敛出来的最佳解法。

这里我们不再关注具体的代码函数细节，从宏观流程上继续我们的网络包旅程。

我们以主流的 Intel 的万兆驱动 ixgbe (Intel(R) 10 Gigabit Ethernet ) 为例，串一下：

  1. 驱动会检查 tx_ring 是否已经满了，满了的话需要打回 qdisc 重新排队
  2. 将 skb 的虚拟地址通过 iommu登记映射并拿到一个 IOVA
    1. 可以把这个机制理解为面向网卡版的 虚拟内存，避免网卡可以通过 DMA 访问任意内存地址导致的安全性问题
  3. 组装 tx descriptor 放入 tx ring
    1. tx ring
  4. 敲 doorbell 通知网卡有包要发送
    1. 首先，为了避免网卡
    2. 驱动在初始化的时候会 mmap 注册一部分卡上的寄存器地址到虚拟内存地址中
    3. 网某个特殊的寄存器写入
