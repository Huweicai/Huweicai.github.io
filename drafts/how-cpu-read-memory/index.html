现代 CPU 是如何访问内存的
  • 2026-01-06
  • 7 minutes read
  • 3100 words

书接上回，我们探讨了如何极致地压榨一颗 CPU 核心，但是当 CPU 自身的计算瓶颈被逐步突破之后，真正限制程序继续变快的，往往不再是 CPU，而是内存。

在代码执行过程中，内存几乎贯穿始终：指令要从内存中取出，数据要从内存中读入，计算结果也要再写回内存。

然而内存的速度远慢于 CPU，CPU 很多时候并不是不想干活，也不是算不过来，只是受累于内存的缓慢在空转等待被拖了后腿。

所以理解程序性能，不能只看 CPU，也要看 CPU 是如何访问内存的。

不同的 CPU 内部架构并不完全一样，尤其是跟早期 CPU 架构相比，这次我们继续仍以当下地表最快商业 CPU i9-14900KS 为例进行分析。

假如我有一个虚拟内存地址

假设我们有一个在 14900KS 性能核心（P-core）上运行的线程，在内存中申请了一块 8 字节的内存，返回的起始虚拟内存地址（Virtual Address，VA）是（0x00007fb46b5ff010）。

0x00007fb46b5ff010 将是我们今天这趟旅途的起点，首先，我们先强调一下这是一个虚拟地址，而不是物理地址，早期计算机是只使用物理地址的，虚拟地址这一机制的引入的历史博弈，这里就不赘述了，简单一句话就是：虚实结合更方便，更安全。

后面的篇幅将围绕这一个虚拟地址展开分为两部分：

  1. 怎么把它翻译成物理地址
  2. 接着怎么读取这个物理地址里的数据。

首先我们先回顾一下 Linux 的虚拟地址内存地址划分：在 64 位操作系统下，理论上内存地址就是 2^64，但是由于这个数字实在是太大了，浪费影响性能，所以 Linux 将高 16 位暂时封存了，只启用了剩下的 2^48 位，并且剩下的内存划分成了用户空间和内存空间两部分，我们申请的这个虚拟地址则位于用户空间：

物理内存的最小单元是字节，每个内存地址对应都是一个字节，直接管理 2^48 个字节是项非常庞大的工程，操作系统通常会引入页的概念来管理一个连续的内存字节块；

过小的页会有更大的寻址开销，而过大的页则往往伴随着更严重的内存碎片问题，权衡之下 Linux 的默认页大小定在了 4096 字节 => 4KB。

开始访问

现在我们来写段代码访问它：

uint64_t x = *(volatile uint64_t *)0x00007fb46b5ff010ULL;

这行代码底层会是一条 MOV 指令，将对应的 VA 的数据读取 load 到 rax 寄存器中：

mov rax, [0x7fb46b5ff010]

CPU 核心内部，前端（Front-End）取到这条指令，将其译码成内部的 load 微操作（uop），派发给后端。

后端识别到是 load uop，就将该操作调度到 LSU（Load/Store Unit）相关通路去执行。

Load/Store Unit

在大学操作系统教材里面大家应该都学过虚拟地址 -> 物理地址映射的多级页表，但是内存实在太慢了，根据局部性原理，现代 CPU 出于性能的考虑引入了 TLB（Translation Lookaside Buffer）对页面映射进行缓存，如果缓存命中就会直接返回对应的物理地址，无需再一级一级查页表了。

i9-14900KS 每个性能核心内部有一套设计到极致的非常精细复杂的 TLB 系统，根据数据类型/读写/页面大小/层级分为多种：

  • L1 ITLB
    • 4KB: 256
    • 2MB/4MB: 32
  • L1 load-only DTLB
    • 4KB: 64
    • 2MB/4MB: 32
    • 1GB: 8
  • L1 store-only DTLB
    • 2MB/4MB/1GB: 16
  • L2 unified TLB
    • 4KB + 2MB/4MB: 1024
    • 4KB + 1GB: 1024

具体到我们这次查询，查询的是普通页面的数据而非指令，LSU 会先查询: 4KB L1 load-only TLB，如果 miss 的话会再查询通用的 4KB L2 unified TLB。

操作系统默认的页面大小是 4KB，在 L1 数据中只有 64 个 entry，相当于只有 256KB 的数据能享受最极致的速度，L2 也只有 4*1024 = 4096 KB；但是如果使用巨页（Huge Page），两个 2 MB 的巨页就能顶整个普通页面的 cache 大小了，能极大地缓解 TLB entry 压力，所以这也是为什么在一些需要极致优化性能的场景，往往都会考虑将一些大块内存使用巨页分配。

页表

如果 L1/L2 TLB 全部 miss 了，那么 hardware page walker 单元就会进行 page walk 去保存有全量地址映射的内存页表中查询。

页表这个结构本质上是要针对 2^36 的稀疏输入，查询对应的 1:1 映射输出；

如果是在实际工作中面对这样的场景我们可能第一个会想到哈希表，map<虚拟页地址, 物理页地址>，但是这是最底层的 CPU 基础设施，哈希表的查询不稳定，另外逻辑复杂很难硬件化，我们肯定不可能用这么不负责任的方案，虽然真有 CPU 方案用过（IBM Power PC）。

X86 的选择是前缀基数树，这也是目前的主流方案，就是按照虚拟地址从左到右依次拆开，拆成五段，

Linux 给这五段各自起了名字，但是其实没有必要记，只需要知道会拆成：

  • 第一级、第二级、第三级、第四级、页内 Offset

这五个部分就行，可以简单理解成省、市、区、街道这种，查地址的时候从左往右开始查；

每一级页表的大小是 512，正好装在一个 4KB 页面中，4096 / 8 = 512，每一个页表里面的表项装着一个 8B = 64bit 的指针，指向下一级页表；这样从左往右一直查就能在最终的第四级页表中查到最终的物理页框号。

物理页框号 + 页内 Offset 一拼，就是最终的物理地址了。

以我们的 0x7fb46b5ff010 为例，这个 64 位虚拟地址只有低 48 位有效（高 16 位是符号扩展，全 0），拆开来看：

0x00007fb46b5ff010

转成二进制后从 bit 47 开始，每 9 位（2^9 = 512）切一刀：

第一级 [47:39]  =  011111111  =  255
第二级 [38:30]  =  011010001  =  209
第三级 [29:21]  =  101011010  =  346
第四级 [20:12]  =  111111111  =  511
页内偏移 [11:0] =  000000010000 =  0x010

另外 CPU 里面会有一个特殊的寄存器，保存第一级页表的地址，Intel 里面叫 CR3，ARM 叫 TTBR0/TTBR1（Translation Table Base Register），RISC-V 叫 satp，功能都是一样的；从这里开始顺着查过去。

于是 hardware page walker 的查询路径就是：

  1. 从寄存器拿到第一级页表的物理基地址，跳到第 255 个表项，读出第二级页表的物理基地址
  2. 跳到第二级页表的第 209 个表项，读出第三级页表的物理基地址
  3. 跳到第三级页表的第 346 个表项，读出第四级页表的物理基地址
  4. 跳到第四级页表的第 511 个表项，读出物理页框号（PFN）

最后 (PFN << 12) | 0x010 = 物理地址。四次内存访问，确定性地完成翻译。

物理地址每次运行可能结果都不一样，这里我们拿到了：PA = 0x0000000d3258d010

CPU Cache 的引入

拿到了物理地址之后，下一步要做的事情，就是加载对应的数据了。

早期的计算机架构中，CPU 主频比较低，以 1980 年代的 Intel 8086 CPU 为例：

  • 8086 @ 5MHz => 一个 cycle 需要 200ns
  • DRAM 访问当时需要 => 250ns

访问 DRAM 只需要 1-2 两个 CPU cycle 的时间就能完成，完全不需要 Cache。

但是后面 CPU 随着摩尔定律制程不断进化，主频一路狂奔，而内存几乎原地踏步；导致直接访问内存会非常非常拖 CPU 后腿：

  • 1980 年 8086 CPU 访问一次内存 250ns ➗ 200ns/cycle = 1.25 cycle
  • 2026 年 14900KS CPU 访问一次内存 80ns ➗ 0.16ns/cycle = 480 cycle

当年速度几乎差不多，现在 CPU 访问一次内存，需要停滞等待 480 个时钟周期啥也不能干，这个期间可以做太多的事情了；这就是上个世纪提出来的 Memory Wall 问题。

后面大家发现 99% 的情况下，CPU 需要访问到的数据其实都具有明显的局部性：

  1. 刚刚访问过的东西，可能马上还要再访问（时间局部性）
  2. 访问过的数据，大概率它旁边的数据也要被访问（空间局部性）

于是 CPU 内部引入了缓存，来缓解这个问题，用一小块昂贵但是比内存快很多的内存，放在 CPU 内部，就能极大缓解 99% 的情况下 CPU 流水线阻塞问题。

至于为什么不直接用这种很快的芯片当主存，主要的原因还是贵，CPU Cache 是用的基于复杂锁存器的 SRAM，一个 bit 要 6 个晶体管，而基于电容的 DRAM 一个 bit 只需要 1 个晶体管 + 1 个电容；

而且还有一个非常致命的问题，面积！

同样大小的 SRAM 内存条，如果要做到 32GB 的话，可能会有一个脸盆那么大。

L1/L2/L3 Cache

以 14900KS 为例，该 CPU 内部，有如下 Cache：

层级 类型 容量 组织方式（Associativity） 作用范围 备注
L0 uOp Cache（微指令缓存） ~4K µops / P-Core 8-way 每个 P-Core 独享 存已经解码的微指令，避免重复 decode
L1 I-Cache 指令缓存 32KB / P-Core 8-way 每个 P-Core 独享 指令读取
L1 D-Cache 数据缓存 48KB / P-Core 12-way 每个 P-Core 独享 数据读取，Intel 特有的 48KB设计
L1 I-Cache 指令缓存 64KB / E-Core 8-way 每个 E-Core 独享 Gracemont架构
L1 D-Cache 数据缓存 32KB / E-Core 8-way 每个 E-Core 独享 Gracemont架构
L2 P-Core 二级缓存 2MB / P-Core 16-way 每个 P-Core 独享 Raptor Cove 最大升级点
L2 E-Core Cluster 二级缓存 4MB / Cluster 16-way 4个E-Core共享 一个E-Core cluster共享
L3 Intel Smart Cache 36MB 12-way 所有核心共享 LLC（Last Level Cache）
